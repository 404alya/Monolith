# Engine code

How to change code. Reference: `docs/architecture.md` (technology, layout, architecture, runtime API), `docs/command-line.md` (controls, flags, environment variables), `.claude/skills/lighting-fog-shadows/r3d-pitfalls.md` (read all of it, with the **`lighting-fog-shadows`** skill, before touching lighting, fog or shadows), `submodules/r3d/patches.md` (before changing R3D), `.claude/skills/benchmarking/measurements.md` (measurements). Larger or multi-agent work: the **`large-engine-work`** skill. After every code change: the **`leak-check`** skill; performance claims: the **`benchmarking`** skill. Before you finish, ask the developer to restart the game: code changes don't hot-reload.

> **R3D changes are patches.** Work around R3D from the app side where reasonable. When R3D itself must change, change it minimally and **record every change in `submodules/r3d/patches.md`** (symptom, cause, files, diff). Never modify other R3D checkouts or projects outside this repo.

## 1. Build and run

```bash
./build.sh              # -> build/linux/monolith + build/linux/maps/  (clang, -O2)
./build.sh run [args]   # build, then run with args
./build.sh debug        # -g -O0 + ASan/UBSan -> build/linux-debug/
./build.sh lsan         # -O1 -g + LeakSanitizer -> build/linux-lsan/; examples: ./build.sh examples lsan (test build)
./build.sh profile      # -O2 -g + frame pointers (R3D/raylib/assimp RelWithDebInfo) -> build/linux-profile/, + its profile tool (tools/profile.c)
build/tools/leakcheck [--asan]     # every main code path under LSan (or ASan + UBSan); exit 1 on a leak
R3D_DIR=/other/r3d ./build.sh   # another R3D tree;  CC=gcc ./build.sh: another compiler
./build.sh --win [run [args]]   # -> build/win/monolith.exe + build/win/maps/ (MinGW-w64); run under wine
./build.sh --tools [name...]    # the programs in tools/ -> build/tools/<name>, build/run-sh.o (only what is stale)
./build.sh examples [--win|test|lsan]   # the examples (examples/nob.c)
./build.sh test [name...] [-- args]     # the unit tests in tests/unit/ (nob.c's UNIT_TESTS: one place for their flags)
```

Both output folders are **self-contained** (copy or zip as-is).

**Tools are C programs, not scripts** (2026-11-13, `docs/architecture.md` §8). A new tool is `tools/<name>.c` on `tools/tool.h` (`ToolInit` first: name, repo root, the rebuild of itself; `ToolRun` / `ToolCapture` / `ToolExec` for commands as argument lists with their exit status; `ToolTrash`; `ToolProgram` for another tool's path) plus its name in `nob.c`'s `TOOLS`; its header comment lists every mode, flag, environment variable, exit code and caller, and every function and step is commented. A new unit test is an entry in `UNIT_TESTS` (`compile_commands.json` follows from it). No new shell scripts: the two `build.sh` launchers are the only ones.

**Every shell command runs through `build/run-sh.o`** (`tools/run-sh.c`, the `PreToolUse` hook in `.claude/settings.json`). It reads the command with a shell lexer (also through wrappers, `xargs`, `find -exec`, nested `bash -c` / `eval`, interpreter one-liners) and refuses, with `run-sh: refused: <rule>: <word>; <what to do instead>` (exit 126):
- **no deletion outside `/tmp`:** `rm` / `rmdir` / `unlink` / `shred` / `find -delete` / `git worktree remove` on anything but a literal path resolving under `/tmp/` (symlinks followed; not in a command line that also makes a link), `git clean`, `git rm` without `--cached`, deletions in interpreter code. Use `gio trash`.
- **no lost work:** `git reset --hard`, `git checkout -- / . / -f`, `git restore` without `--staged`, `git stash drop / clear`, `git switch -f`.
- **no visible window:** the game without a windowless flag (old binaries from `old-monolith` too), the plain examples, setting `MONOLITH_ALLOW_WINDOW`.
- **never touch the screen:** `i3-msg` / `swaymsg` other than `-t get_*`, `xdotool`, `wmctrl`.
- **benchmarks:** `--bench` without `--headless`, `__GL_SYNC_TO_VBLANK=0` or `--note`; a second one while one runs (a lock held for the run's lifetime).
- **stay in the repo:** literal write targets (redirections, `cp` / `mv` / `tee` / `mkdir` / `touch` destinations) outside the repo and `/tmp`.

`run-sh.o --check '<command>'` prints the decision without running anything; the log is `build/run-sh/log`. It sees only the text: what exists only after expansion (`"$X"`, `$(…)`), scripts a command runs and compiled programs are not checked, and prose inside a Python heredoc that names a deletion is refused (edit files with the file tools). In bypass / auto / dontAsk sessions the command is rewritten into `run-sh.o -c '…'` (always bash, a `cd` doesn't carry over); in prompting modes it is only checked, so allow rules keep matching. A rule change goes into `tools/run-sh.c` with a row in `tests/unit/run_sh_test.c` (`./build.sh test run_sh`). If `run-sh.o` can't be built the hook blocks every command: fix `tools/run-sh.c` with the file tools, or the developer turns the hook off in `/hooks`.

**The build program.** `build.sh` is only a launcher: it compiles `nob.c` (repo root, C11 on the vendored nob.h 3.10.1, `src/vendor/nob/`, unmodified) into `build/nob` when that is missing or older than `nob.c` / `nob.h`, then `exec`s it with its arguments (`build/nob` run directly rebuilds itself too, `NOB_GO_REBUILD_URSELF`). Everything else is in `nob.c`: `BuildR3D` (configure + incremental cmake build, the args file), `Xatlas` (object + `.flags` stamp; recompiled when xatlas, `nob.c` or the flags changed), `BuildLinux` / `BuildWindows` (the game's command, the `maps/` copy, the OFL files), `WriteCompileCommands` (a C port of the old embedded Python: byte-identical JSON, no python3 needed).
- **Every command goes through `RunTimed(cmd, label, output)`**, never `nob_cmd_run` directly and never `.async`: it echoes `[INFO] CMD: …`, runs the command, and prints `[TIME] <label>: wall, CPU (user + sys)`; a summary table ends every build (and precedes `run`'s hand-over to the game). CPU time is the `getrusage(RUSAGE_CHILDREN)` difference, which counts every process the command waited for (all of `cmake --build -j`'s compilers): exact only because commands run one at a time. No cycle counts (the developer chose time only).
- **Output:** `[INFO]` / `[TIME]` lines and the progress lines (`configuring …`, `building R3D …`, `built: …`, `wrote: compile_commands.json`: keep their text, scripts read them) go to stdout, errors to stderr, so `./build.sh lsan > /dev/null` (the leak check) stays quiet. A log redirect (`> log 2>&1`, `>> log 2>&1`) is `RunTimed`'s `Output{.log, .append}` (it points fds 1 and 2 at the log around the command; nob's `.stdout_path` / `.stderr_path` can't share one file or append).
- **Add a flag:** put it in the argument list of the command it belongs to, in compiler order, with a comment saying why; if that list is mirrored in `compile_commands.json` (the examples', `tests/unit`'s, `tools/profile.c`'s entries copy their scripts' flags) keep the entry in step. **Add a mode:** a branch in `main()` / `BuildLinux()` choosing its output folder and flags, its commands through `RunTimed`, its doc line at the top of `nob.c` and in the usage list above. Shell-isms are mirrored on purpose: `${VAR:-x}` (`Env`), `$(cat f)` (`ReadTrimmed`: trailing newlines stripped), `-nt` (`NewerThan`, ns mtimes), bash glob order (`AppendGlob`, `LC_COLLATE`), `nproc` (`Nproc`: affinity + `OMP_*`).
- **Prove a build change** like the nob round did: tool wrappers first in `PATH` that log their argv and exec the real tool (`exec` the real path, not `exec -a`: cmake finds its root through argv[0]), old vs. new argv logs diffed per mode, sha256 of every output. Set `SOURCE_DATE_EPOCH` for `--win`: without it the PE link timestamp makes two builds of the same code differ. Edge cases that would force a full R3D rebuild (`R3D_BUILD_TYPE=None`, other compilers) as a dry run with stub tools that only log, against a scratch `R3D_DIR`. Pass such argument lists as arrays or literally, never as one unquoted `$var`: a script waiting for a `--` that never arrives loops forever (it hung the machine once in zsh).

**`compile_commands.json`** (repo root, gitignored) is generated by the plain `./build.sh` from the same flag lists it compiles with (`nob.c`'s `WriteCompileCommands`), plus R3D's CMake export (assimp dropped); never hand-edit it. A new `.c` in `src/` or `runtime/` is picked up automatically; a new example or `tests/unit` program, or a flag change in `./build.sh examples` / `tests/unit/*.sh`, needs its entry in `nob.c` too (they're mirrored there).

**R3D** is built by the build (`nob.c`'s `BuildR3D`): configured on first use in `$R3D_DIR/build-linux` / `build-mingw` (a few minutes, assimp), then an incremental `cmake --build` each time (~1 s no-op; log in `<build dir>/monolith-build.log`). Delete the build dir to force a fresh configure.

**Linux:**
- R3D config: static, vendored raylib + assimp + zlib (`ASSIMP_BUILD_ZLIB`), bundled minizip (`ASSIMP_BUILD_MINIZIP`; a system minizip breaks the build), no examples, GPU profiler compiled in (`R3D_GPU_PROFILER`, on only under `--bench`; patch 5), `CMAKE_BUILD_TYPE=Release`. Options are remembered in `build-linux/monolith-configure.args`; a change re-configures (full R3D rebuild). `R3D_BUILD_TYPE=None` gives the old unoptimised build; any other value is passed as `CMAKE_BUILD_TYPE`. Bench reports state the R3D build type (no measurable difference: `.claude/skills/benchmarking/measurements.md`).
- Links R3D, raylib, assimp, zlib and **libstdc++ statically** (`-l:libstdc++.a`). Runtime deps only `libc`, `libm`, `libgcc_s.so.1`, `libGL.so.1` (check: `readelf -d build/linux/monolith | grep NEEDED`).
- **glibc ≥ 2.34.** The build passes `-Wl,--wrap=` for newer symbols and `src/glibc_compat.c` routes them to old versions (libm to `@GLIBC_2.2.5`, `arc4random` → `getrandom`, `__isoc23_strtoul` → `strtoul`, `__isoc23_strtol` → `strtol`). After changing compiler, glibc or dependencies, `objdump -T build/linux/monolith | grep -o 'GLIBC_[0-9.]*' | sort -uV | tail -1` must still print `GLIBC_2.34`; add any newer symbol to `glibcWrap` in `nob.c` and `glibcWrap` in `examples/nob.c` (two copies of the list) and to `glibc_compat.c`.
- A portability test on this machine still uses the repo paths unless they're hidden: `unshare -rm sh -c 'mount -t tmpfs none <repo path> && /path/to/copy/monolith --shot /tmp/x.png --view 2'`. x86-64 only.

**Windows (`--win`)**, `x86_64-w64-mingw32-gcc`:
- R3D in `$R3D_DIR/build-mingw` with `cmake/mingw-w64-x86_64.cmake` (Release, static). The exe is **fully static** (`-static`): `build/win/` is `monolith.exe` + `maps/`, no DLLs. Imports only system DLLs (`opengl32`, `gdi32`, `user32`, `kernel32`, `shell32`, `winmm`, UCRT `api-ms-win-crt-*`); check with `x86_64-w64-mingw32-objdump -p build/win/monolith.exe | grep "DLL Name"`.
- The **view-only build** (`MONOLITH_EDITING` 0 in `src/common.h`, keyed on `__linux__`): editing and request keys and flags are refused at their entry points with `MSG_VIEW_ONLY` (`src/main.c` header, "View-only build"); `launcher.c` and `import.c` are POSIX and left out of `BuildWindows`' source list (their headers give `static inline` stubs). Gate a new editing entry point with `if (!MONOLITH_EDITING)` (not `#if` around code) so both builds keep compiling every module, and add its key / flag to that list, `keyspanel.c` (`EDITING` rows) and `docs/command-line.md` "View-only build". Test refusals under wine with `--input-script` + `--shot --shot-hud` (F9, the K keys and the id panel act in scripted shots there: `liveKeys` in `main.c`).
- Console-subsystem exe (bench tables and **P** output visible). Bench reports go to `build/win/benchmark/`. `--win debug` is refused (no sanitizers with MinGW).
- Verify under wine (host GL driver, shots pixel-identical to Linux): `wine build/win/monolith.exe --shot win.png --view 2`. wine's `MESA-EGL: warning` lines on NVIDIA are harmless.

A change is done only when it **builds with no warnings** on both targets, **`build/tools/leakcheck` reports zero leaks**, and it has been **checked visually** (§3).


**Memory rules:**
- **No fixed-size content buffers.** Anything sized by content (map objects, lines, selection, regions, prompt, open requests, child processes, bench frames, export file lists) is a heap array (`MS_RESERVE` / `MS_PUSH`, `runtime/monolith_scene.h`, used by `src/` too) or a heap string (`MS_StrDup`). Fixed `char` arrays only for stack scratch formatting one path, and single values the loader bounds; text for people is a `MonoMsg`, a `MonoStrf` string, the last error or a literal (below).
- **Errors go into the runtime's last error, a heap string with no length limit.** A function that can fail returns NULL / false / `MS_RELOAD_FAILED`; the reason is `MS_LastError()` (per thread, `_Thread_local`). No `char *err, int errSize` parameters and no `char err[N]` buffers, in the runtime or in `src/`. Inside the runtime: `ErrSet` / `ErrAppendF` (and `ErrAt` / `ErrPutV` for a `file[:line]: ` prefix; the parser's `Fail` / `FailF`, the compiled-map reader's `CmFail`); in `src/`: `MS_SetError` / `MS_AppendError` (both return false: `return MS_SetError(…)`). Pass content (tokens, names, paths, lists) as arguments or append it piece by piece; never pre-format it into a local `msg[]`. A new message is built before the old one is freed, so it may quote `MS_LastError()` (to prefix it). The runtime's reporting functions clear it on success; `src/` functions set it only on failure, and a caller reads it only right after a failure (it is valid until the next `MS_*` call: copy it with `MS_StrDup` to keep it, as `MS_Error(scene)` and the launcher do). A file read whose failure isn't the caller's failure passes `report = false` to `ReadWholeFile`. Out of memory while building a message: `"out of memory"` (static). Programs call `MS_ClearError()` at exit (the editor's `main`, every example); a thread of your own calls it before it ends.
- **Results are status codes; text for people is kept apart** (2026-11-09, `src/msg.h`). A function that can fail or end in several ways returns a plain `unsigned char`: 0 = success, 1, 2, … the other outcomes, listed in the comment above it (header and definition); no enums, typedefs or `#define`s for them. Callers compare with the number (`if (MapEditSave(E) == 2) // not saved`), never `if (!Fn())` (the polarity is POSIX, the opposite of the old `bool`), and never branch on a message (`msg[0]`, `strstr`, an empty string). No `char *msg, int msgSize` out-parameters and no `char msg/note/message/status[N]` for text that is logged or shown. Each code's sentence has one place, named in the comment: `MS_LastError()` for failures (set with `MS_SetError`), the owner's note for the other outcomes (a `MonoMsg`: `MapEditNote(E)`, `LauncherNote()`, `ExportNote()`), or a literal the caller picks by the code. If the caller only printed or showed the text, the callee reports it itself (logs it, or posts it to the HUD it owns: `EditModeSave`, `ExportScene`). Stored HUD texts are `MonoMsg` (`{ const char *text; char *owned; }`): a literal through `…Static` (`SayStatic`, `DesignerMessageStatic`, `SpectatorMessageStatic`, `PanelStatusStatic`, `MsgSetStatic`: never copied, never formatted, never freed; passing anything that doesn't outlive the message is a dangling pointer), run-time text through `…f` (heap, sized to fit), freed by the owner. One-off formatted text: `MonoStrf` (free it). `TextFormat` is a 1024-byte rotating buffer: only for text bounded by a few numbers. raylib's `TraceLog` formats its arguments unbounded (only the format string is limited), so log long text as an argument. Set a message when it changes, never every frame.
- **Sanity caps instead of limits**, each with a clear message: `MS_MAX_OBJECTS` (1 000 000 boxes + model instances + lights), `MS_MAX_FILE_BYTES` (4 MB map), `MS_PATH_MAX` (1024), 3 `repeat`s per line, a 1 MB prompt, `BENCH_FRAMES_LIMIT`.
- **The per-frame path never allocates** (drawing, picking, HUD, collision): scratch arrays grow to the largest size seen. Allocation happens on (re)load, input events, submit / export / report.
- **Everything is freed** (`MS_Unload`, editor state at exit); the leak check proves it.

## 2. Common modifications

**Edit or start a level.** Edit the package following its `MAP.md` (format: `docs/map-format.md`; rules: the `map-editing` skill); it hot-reloads, no rebuild. New level: `--new-map <name>`, fill in `MAP.md`, build (or submit a first request: the session writes the brief first), or `--import` a raylib + R3D project. Models: the `assets-and-licences` skill.

**Add a map primitive or statement.** A builder next to `Box`/`Block`/`Stairs`/`WaffleFacade` in `runtime/monolith_scene.c` plus a `PRIMS[]` entry (name, argument count, per argument its shift axis `AX_X/Y/Z`, `AX_NONE` for sizes, `AX_INT` for counts), and its call where `ParseStatement()` dispatches. That code switches on the argument count (box and block, both 6, differ by `PRIMS[]` entry), so a new 6–8-argument primitive means switching on the entry. Builders return false when the map is full (`MS_MAX_OBJECTS`) or out of memory, and loops add a box per iteration so the cap bounds them. A new statement or key is part of the current format: older runtimes refuse it with a line error, and every existing map still reads the same, so it needs no bump. Anything that changes how an existing map reads or makes it fail is a format change (next paragraph). **Compiled maps** (`docs/compiled-map.md`, region "Compiled maps"): a statement that only makes boxes needs nothing more (boxes are stored expanded), but anything new the parser stores in `SceneData` (a field, a list, a new kind of object) needs a compiled record or field: written by `WriteCompiled`, read and checked by `ReadCompiled` (with the parser's own limits), the layout in `docs/compiled-map.md`, and `CM_VERSION` bumped (the one rule: any change to a record or section, even one that keeps a record's size, bumps it; there are no layout asserts); then the round trip (§3, step 9) and `./build.sh test compiled`. Document it in the `monolith_scene.c` header comment and `docs/map-format.md` §2. Manual edits (`src/mapedit.c`, `Analyze`) learn a new box primitive's position arguments from `PRIMS[]` through `MS_PrimitiveArgs`; a new statement of another shape (like `light` / `model`) needs its position numbers added to `Analyze`, or the edit mode can't move it. Manual edits are live (`docs/live-editing.md`): `MS_EditSetText` carries over every GPU resource that doesn't depend on objects, so anything new that a statement uploads or caches must either be carried over there or make the non-object hash differ (a full upload); a new static cache must take the dirty regions (re-stamp, invalidate what they reach), and `--edit-script` vs. `--apply-edits` shots (0 changed pixels) are the test.

**Code that reads boxes** (`scene->boxes[]`, `colliders[]`): a box can be turned (`box … rot`, `docs/live-editing.md` §11). `boxes[i]` / `colliders[i]` of a turned box is its **world AABB**, right for bounds, culling, clusters, dirty regions and broad phases; anything that needs the exact shape (collision, picking, outlines, meshing, the AO volume, dumps, the compiled record, bundles) checks `scene->boxTurned && scene->boxTurned[i] >= 0` and uses `turnedBoxes[]` (centre, size, axes). Keep the axis-aligned path unchanged and the turned one behind that check, so maps without turned boxes stay bit-identical; the player lands and steps through `MS_ColliderTop` / `MS_ColliderBottom`, never `max.y` / `min.y`. Scripted input (`--input-script`) has key `down` / `up` but only mouse clicks, so a drag with the button held (the gizmo's release-to-commit) is tested by hand.

**Change the map format** (one version in the code, `project-history`, 2026-11-12). Monolith reads exactly one version of each of its own formats: the map text (`MS_FORMAT_VERSION`), the compiled map (`CM_VERSION`) and the request bundle (`"format"`). The number is a guard, never a branch: no code reads an older version, and nothing migrates in C. A change that removes or changes the meaning of anything in the map text, in the same change:
- bumps `MS_FORMAT_VERSION` (numbers are never reused or reset) and updates the header comment in `monolith_scene.c` and `docs/map-format.md` (§1.3, §2);
- adds the entry `N → N+1` to `.claude/skills/migrate-map/versions.md`: the rewrite rules with before/after lines, whether it is lossless, the proof expected, and `last-reader:`, the newest commit that still reads N (usually the commit the change starts from; check that `build/tools/old-monolith <commit>` builds it);
- migrates every map in the repo with `/migrate-map` (the `migrate-map` skill: `maps/`, the gitignored maps too, `tests/models`, `tests/rotated`, the examples' maps), plus the `--new-map` template (`src/newmap.c`), the capture shim (`runtime/monolith_capture.h`) and every test or tool that writes map text (`tests/unit/`, `build/tools/leakcheck`);
- adds a `tests/unit/parse_error_test.c` case: the previous version is refused with the migration message.
The compiled map and the bundle are never migrated: a `.mapb` is compiled again, and old bundles are left alone. Their readers accept only the current version.

**Add an environment key.** Key tables in `monolith_scene.c` (region "Key tables": `ENV_KEYS` for `R3D_Environment` fields, sky / sun tables otherwise, a range in `ENV_RANGES`; any other check in `CheckEnvValue`, which the text parser and compiled maps share), its built-in default in `BuiltinEnvironment()` equal to today's value, written by `MS_WriteEnvironment`. Compiled maps store env keys by name, so a key of an existing type needs no format change; a new value type (`T_*`, appended at the end) needs `CmPutEnv` / `CmReadEnvRecord` and a `CM_VERSION` bump. Image changes without a reload must reach `FrameKey`.

**Change a request bundle.** The C strings in `src/launcher.c` (`request.md`, `request.json` `instructions`, the coordinator's start prompt) and `src/import.c` name `CLAUDE.md`, `.claude/skills/map-request/SKILL.md` (and its section 3), `.claude/skills/import-request/SKILL.md` and `.claude/skills/coordinator/SKILL.md`: don't rename, move or renumber those without changing the strings in the same change. `launcher.c` (`BuildBundle`, `WriteRequestMd`, `WriteRequestJson`; bump `"format"` when keys change) and `.claude/skills/map-request/bundle-reference.md` (it describes only the current format: older bundles are not read or migrated; the `map-request` skill if the workflow changes); `build/tools/request-queue` (`tools/request-queue.c`) reads `kind`, `prompt`, `model` and the first `"package":` line from `request.json` line by line. New terminal: `TERMINALS[]`.

**Add a viewpoint.** Spectator mode, **P** (prints *feet*), then `viewpoint "Name" ex ey ez tx ty tz` with the *eye*. `--bench` covers it automatically.

**Tune a map's look / shader.** Its `env` lines, materials and `shaders/` (hot-reloaded); respect `.claude/skills/lighting-fog-shadows/r3d-pitfalls.md` §1–5 (the `lighting-fog-shadows` skill) and the map's `MAP.md`; check shaders with `glslangValidator`. Changing a map's look needs the developer's approval.

**Add a graphics setting.** A field in `MS_Quality` (preset values, `MS_QualityEqual`, `MS_ApplyQuality`), the file key and panel row in `settings.c` / `settingspanel.c`; ultra stays the map exactly.

**Add an effect toggle.** The `TOGGLE(KEY_x, 'x')` block in the main loop, the HUD string, the header comment.

**Draw editor text or a panel.** The look is `docs/ui-design.md` (tokens, type roles, shapes, states): read it first. Through `src/ui.h` only (`UiText` / `UiTextBold` / `UiMeasure`, `UiTitle` for panel titles, `UiHudText` / `UiHudHints` / `UiHudMark` for top-left HUD lines on their backdrop, `UiHints` markup for keys: `{KEY}` cap, `|` separator, `~off~`, `^on^`; `UiSheet` for a panel, `UiMark` for a status, `UiToast`, the widgets), with the type-scale sizes (`UI_XS` … `UI_XL`) and colour tokens. **Token rules:** no `(Color){…}` literal for UI in a module: surfaces are black with alpha, text white at the alpha tiers (`UI_HOT` / `INK` / `TEXT` / `BODY` / `DIM` / `FAINT`), colour only as meaning (`UI_CHANGED`, `UI_OK`, `UI_WARN`, `UI_ASK`, `UI_ERROR`, the mode colours) and only as a status mark (2 px bar + text); a new meaning gets a token in `ui.h` and a row in the spec. Scene-side colours (outlines, region / volume frames, gizmo axes, paint) stay module constants, and the request images' labels stay `UiTag`, so `view-marked.png` doesn't change with the UI's look. `raylib`'s `Fade` replaces alpha: to scale a token's alpha multiply it (`ui.c`'s `Mul`); never `DrawText` / `MeasureText` / `GetFontDefault` (raylib's font), and no other size: the atlas holds only the scale. Measure and draw with the same helper and size (the prompt box wraps with `UiAdvance`), or the cursor drifts. Text is drawn at integer positions. No `DrawRectangleRounded*` in the overlay: they emit dozens of triangles and switch the batch's draw mode, and with ~60 key caps they cost +0.13 ms a frame (more than the whole UI before); `UiPanel` / `UiPill` / the key caps draw rounded shapes from the atlas instead. Time an overlay change with an instrumented build (glFinish before and after the UI block, average over `--bench-still --frame-reuse --bench-window 4`): whole-frame benches on a laptop are too noisy to see tens of microseconds. Keep `{ } | ~ ^` out of markup that contains map data (group or file names): draw that with `UiHudText`. The runtime, `runtime/export/` and the examples stay on raylib's font. **Change the font:** put the static `.ttf` files and their `OFL.txt` in `resources/fonts/<name>/` with an `ASSETS.md` row and sidecars (the `assets-and-licences` skill), regenerate `src/font_outfit.h` with the command in `tools/embed_font.py` (run under `python3 -I`), adjust `EM_TO_PX` in `ui.c` to the font's ascender − descender, and take `--shot-hud` before/after images.

**Add a CLI flag.** Parse it at the top of `main()`; a new mode that opens no window or only a hidden one also goes into the `windowless` check after the flag loop (otherwise the game refuses it in an agent's shell); document it in the header comment and `docs/command-line.md`.

## 3. How to verify changes

No test suite; verification is **visual and numeric**:

1. **Build cleanly:** `./build.sh` and `./build.sh --win`, no warnings; `./build.sh examples` (and `--win`, `test`) when the runtime or an example changed. The examples are plain integration code (no tool flags); `--shot` exists only in their test build, `tests/examples/harness.h` force-included by `./build.sh examples test` / `lsan`: keep test hooks there, not in the examples. Shaders pass `glslangValidator`.
2. **No leaks:** `build/tools/leakcheck` ends with `leakcheck: OK: zero leaks of ours` (the `leak-check` skill). After larger changes also `--asan`.
3. **Every map is unchanged** by engine work: for each map in `maps/` (and `tests/models` when models, materials, lights or environment code changed), identical `--dump-boxes` and pixel-identical `--shot`s against a build from before the change: every viewpoint, yaw sweeps 0/60/…/300 from one position at a few eye heights, a `--reload-test`, plus the extra views the map's `MAP.md` lists under *Engine verification* (if it has that section). Rendering is deterministic (the same build gives the same image on every run; R3D patch 17 fixed draw order that followed heap addresses): a shot that differs between two runs of one build is a bug, so check with two runs of the new build before blaming the change.
4. **Fixed views:**
   ```bash
   ./build/linux/monolith --shot a.png --view 2                          # viewpoint 2
   ./build/linux/monolith --shot b.png --pos 0 0 -5 --look 120 5         # exact view
   ./build/linux/monolith --shot c.png --view 2 --off 16                 # effects off
   ./build/linux/monolith --shot d.png --view 3 --map maps/<name>         # another package
   ```
   For lighting or shadows, take a **yaw sweep from one position**: the black-curtain and shadow-popping bugs only showed when rotating.
5. **Isolate effects** with `--off` (1 volumetric fog, 2 fog, 3 SSAO, 4 SSIL, 5 bloom, 6 sun).
6. **Performance:** the `benchmarking` skill.
7. **Window titles:** automated runs are titled `monolith-bench` / `monolith-shot` (also the examples' test build), normal play `monolith`; a window-manager rule can move the first two out of the way (i3: `for_window [title="^monolith-(bench|shot)$"] …`). Keep these titles. Request terminals: `monolith-claude: coordinator`, per-request mode `monolith-claude: <slug> <HHMMSS>`.
8. **Movement** (collision, controls) can only be tested by playing.
9. **Map loader and edits:** diff `--dump-boxes` / `--dump-scene` / `--dump-scene-diff` before and after (identical for every map after a loader change). After a change to the parser, the compiled format or `SceneData`: the **round trip** too: `--compile` every map in `maps/` and `tests/models` into a scratch copy of its package (twice: byte-identical), then its `--dump-*` (all but the `map "<path>"` line) and `--shot`s from the `.mapb` must equal the text's; `./build.sh test compiled` (corruption test and long messages, ASan + UBSan), `./build.sh test parse_error` (the parser's messages) and `./build.sh test export_strip` (the export's runtime has no parser). A broken map prints `file:line: message` and exits 1 before any window; the running game keeps the old map. Hot reload runs only interactively; `--reload-test` exercises it in a shot.
10. **Designer and launcher without a window:**
    - `--shot x.png --view n --pick` must still report the same hit as before the change (the map's `MAP.md` may list a reference pick under *Engine verification*).
    - `--shot-hud` with `--select` / `--region` / `--type` / `--settings-panel` puts the overlay into the shot.
    - `--submit` **always** with `MONOLITH_REQUESTS_DIR=<scratch folder>`, `MONOLITH_TERMINAL=build/tools/stub-terminal` (logs to `$MONOLITH_STUB_LOG`) and `MONOLITH_WORKSPACE=`; `gio trash` the folder afterwards. `build/tools/test-coordinator` tests the queue end to end (one terminal for many submits, scheduling, cancel, recovery after killing the coordinator, per-request mode). `--classify` checks the model choice without a bundle.
    - Mouse and keyboard input: `--input-script` plays scripted keys, clicks and mouse motion through the interactive input path in a hidden `--shot` (`src/input.c`: every `src/` module reads input through it, so call raylib's input functions only via `common.h`); the feel of a real mouse and GLFW itself can only be tested by hand.
11. **Export and examples:** export into a scratch folder and build it there (its `build.sh`). The exported viewer and the game-style examples load the compiled map; moving the export's `.map` out of its package must not change a shot. Its `viewer.c` has no screenshot flag: render it with the test harness (compile `viewer.c` with `-include <repo>/tests/examples/harness.h -I<repo>/runtime` and run with `--shot`), or with `examples/build/linux-test/01_minimal/minimal <export>/<map> --shot … --view n`; compare with `monolith --shot … --view n` (pixel-identical for the shipped packages).

## 3a. Export changes

After changing the export, the runtime's editor blocks, `runtime/export/*` or what R3D's build reads: export every map in `maps/` (and `tests/models`) into a scratch folder, copy each into a fresh folder and run its `./build.sh` (and `--win`), then render every viewpoint with a scratch harness linked against that package's runtime and bundled R3D (hidden window, 1600 × 900, FXAA, `MS_InitRenderer`, 30 frames into a `RenderTexture`) and compare with `monolith --map … --shot … --view n`: they must match. Grep the package for tool leftovers (`--shot`, `bench`, `hidden`, `MS_Poll`, `reload`, `editor`, `request`, `Claude`): only the map's own files (its comments, `MAP.md`, `ASSETS.md`) and R3D's own sources may hit.

## 4. Conventions

- **English** for code, identifiers, comments and names.
- **Match the style:** 4-space indent, `static` functions, PascalCase functions, `UPPER_CASE` macros, `// #region` sections, short comments explaining *why*.
- **Layout of record structs and longer functions** (the model: region "Compiled maps"): a struct is multi-line, one group of related fields per line, with a comment above it (what it is, where it comes from, what its less obvious fields mean) and a blank line between structs. Every function has a header comment; longer ones separate their steps (check, fill, store) with blank lines and a one-line comment where the reason isn't obvious. Long conditions go one clause per line, dense designated initializers one field group per line, wrapping at about 110 columns (a message string stays whole). A layout-only change is proven by the token stream: `gcc -fpreprocessed -dD -E -P <file> | tr -d ' \t\n'` before and after must be identical.
- **Small result states needn't be `int`:** a 0 / −1 return code (like `fseek`'s) or a 0/1 state may be held in `signed char`, with an explicit cast from the `int` that produced it. Write `signed char`, never plain `char` (unsigned on some targets).
- **One module per concern:** each `src/<module>.c` has a `.h` interface and a header comment; file-local functions `static`; minimal shared state (`scene`, data paths).
- **The runtime stays portable:** `runtime/` depends only on raylib and R3D, compiles without `MS_PATCHED_R3D`, knows nothing about the editor. The text parser is editor-only: code the game build needs (the compiled-map reader and what it checks with) stays outside the `MONOLITH_EDITOR` blocks and must not parse map text. Editor-only code stays in `src/`; tool-only code inside `runtime/` goes into `#ifdef MONOLITH_EDITOR` blocks (never nested; `#ifndef MONOLITH_EDITOR … #endif` for game-only code, `#else` allowed). Comments outside those blocks ship with `--export`, so they must not mention the editor, requests, Claude Code, hot reload or monolith's command-line flags. The runtime builds with zero warnings with and without `MONOLITH_EDITOR` (and without `MS_PATCHED_R3D`): check all three after a runtime change.
- **The level is data:** geometry, materials, lights, environment live in `maps/<name>/`; C describes primitives and statements, not buildings or a look. Nothing outside a package assumes a style.
- **Assets are recorded** (`ASSETS.md` row + sidecar; CC0 / PD / CC-BY with attribution).
- **Memory:** heap arrays for content, no per-frame allocation, everything freed (§1, memory rules).
- **Comment non-obvious engine workarounds** with their reason (as for R3D pitfalls §1, §2), so nobody "cleans them up".
- **Don't commit `build/`, screenshots, `benchmark/`, `requests/` or `export/`.**
- **Keep the docs current** in the same change: `src/main.c`'s header comment (controls, flags), `docs/architecture.md` (layout, architecture), `docs/command-line.md` (flags), `docs/user-guide.md` (keys, settings), `docs/request-queue.md`, `docs/troubleshooting.md` and `docs/glossary.md` where they are affected, `CONTRIBUTING.md` (rules for people), `.claude/skills/lighting-fog-shadows/r3d-pitfalls.md` (pitfalls, with "if R3D changes X, update Y" warnings), `map-format.md`, the skills when a workflow changes, `patches.md`, measurements in `.claude/skills/benchmarking/measurements.md`.
