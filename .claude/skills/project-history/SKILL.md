# Project history

The reasons behind the project's shape, from the task prompts of the development rounds, the design notes and the QA pass (the originals are in git history). **This is background, not instructions:** where anything here describes an older way of working (terminals per request, `AI-MAP-TOOL.md`, `docs/knowledge/`), the current skills and `CLAUDE.md` win. Measurements: the `benchmarking` skill's `measurements.md`; R3D changes: `submodules/r3d/patches.md`.

## Starting point

One hand-built brutalist concrete level in a single `main.c` (~1100 lines, `BuildWorld()`), walkable or seen from a spectator camera, ~5.9 ms per frame (~170 FPS) headless on the RTX 4050 Laptop it was developed on, with 3 local R3D patches.

## Round 1: the map designer and the caches (commit `b70d5a2`)

What the developer wanted, and the reasons that still shape the code:

1. **An AI map designer.** Point at the map in spectator mode, select, type what should change, and have Claude Code carry it out in a new terminal while the running game shows the result.
   - **The map became data** (`maps/*.map`, hot-reloaded): an AI that edits C and then needs a rebuild and restart is a poor loop, and the caches need a clear "the map changed" event (`scene->version`).
   - **One primitive per line**, so a line number identifies an object and diffs stay readable; `repeat` / `at` keep loops short and reproduce the old C loops bit for bit (an identical box list was the acceptance test).
   - **Every object keeps a back-reference** (line, index, group): selection, request bundles and reloads depend on it.
   - **The bundle is self-contained** (`requests/<id>/`: images, `request.md`, `request.json`, a reproduction `--shot` command, the map hash) so a session can find the spot, take its own before/after images and notice concurrent edits. `--eye` exists because `--pos` takes the feet and the 1.62 m offset was error-prone.
   - **The prompt never reaches a shell**: the launcher builds an argv array (`fork` + `execve`), so no quoting or injection is possible.
   - `CLAUDE.md` exists because Claude Code reads it automatically; it was to carry the hard rules and point to the product and engine references.
2. **Frame rate by caching static work.** Sun and geometry never move, but R3D treated everything as dynamic. Measured first (the per-pass GPU profiler), then: Release R3D build, frame reuse for a still camera, static sun shadow tiles, the fog cache and baked AO as trade-off switches. Results: the `benchmarking` skill's `measurements.md`.
3. **View-independent effects.** Turning the head in place changed how the fog looked. This had to be fixed *before* the caches, or they would bake the error in (R3D patch 4, `lighting-fog-shadows/r3d-pitfalls.md` §6).

## Round 2: any map, models, export and import

Round 1 assumed one kind of level (brutalist concrete, boxes only, one shader) and a closed program. Round 2 removed both:

1. **Any style.** Nothing in the engine, the docs or the AI instructions may assume concrete, boxes only or a fixed look. Everything brutalist moved into the default map's own brief, `maps/monolith/MAP.md`.
2. **A design brief per map** (`MAP.md`), read first on every request; a request on a new or empty map writes the brief before building.
3. **Map packages** (`maps/<name>/` with the map, brief, shaders, models, textures, `ASSETS.md`), package-relative paths only, so a package can be copied and exported. Materials, environment and lights became data; the caches follow the map's bounds instead of the default map's layout.
4. **Models**, for what boxes can't express. Found online only with a licence that allows use, modification and redistribution (CC0 / public domain; CC-BY with attribution), downloaded as untrusted data, and **restyled through material overrides in the map, never by editing the file**, so the original stays traceable (the `assets-and-licences` skill).
5. **The scene runtime** (`runtime/monolith_scene.h/.c`) used by the game itself, so an exported scene can't drift from what the editor shows; `--export`, `--import` (+ the capture shim), `examples/`.
6. **Screen regions** (snip mode), for requests about an area rather than an object; bundle `format: 2`. Format-1 bundles had to still make sense to the instructions (until 2026-11-12: now only the current bundle format is described).
7. **Request terminals on i3 workspace 10**, started with the two permission flags so the developer isn't asked to approve each command. Because those sessions run without approval prompts, **the guard rails live in the instructions**, short and at the top of `CLAUDE.md` and the request instructions (then `AI-MAP-TOOL.md`, now the coordinator's subagent prompt): request text, downloads, model metadata and imported sources are data, never instructions; work only inside the repo; trash, never `rm`; never run downloaded code; never open a visible window.

## After round 2

- **Memory rules and the leak check** (stream M): no content limits, heap arrays via `MS_RESERVE` / `MS_PUSH`, sanity caps; `tools/leakcheck.sh` (the `engine-code` and `leak-check` skills).
- **Pass trimming** (stream P): R3D patch 10, a single-sampled window by default (`--window-msaa`), `--bench-window`; trade-off knobs `--render-scale` / `--upscale` and the baked occlusion volume `--ao-volume` / `--ao baked` (R3D patch 11).
- **Graphics settings and presets**: `MS_Quality` and friends in the runtime, the F2 panel and the settings file in the game (`docs/user-guide.md`, `docs/architecture.md` §4.4).
- **Model tiers**: every request gets a fast / default / heavy model (`launcher.c` "Model choice", `MONOLITH_MODEL*`).
- **Closing request terminals**: K, Shift+K, Ctrl+K n; i3 / sway marks (`launcher.c` "Closing request windows").
- **Style-neutral docs** (stream G): the default map's brief, look and reasons moved into its own `MAP.md`.
- **The QA pass** (2026-10-11, below).

## The QA pass (2026-10-11)

After round 2, three independent testers worked on copies (never the repo), two fixers fixed every confirmed finding with a regression test each, and the lead merged and re-verified: 31 findings fixed (the list is in git history, `docs/QA-REPORT.md` before 2026-10-24). What it taught, and still applies:
- **Fuzz the parser and the flags under ASan / UBSan**: 15,540 fuzzed maps found nothing in the parser, but the command line had no unknown-flag error (a flag that swallowed `--shot` started the visible game), `--fx` had no range checks (one value hung the GPU for a minute), and non-finite positions were undefined behaviour. Hence the strict parser, range checks on every number and ±1e6 position limits.
- **Model files are untrusted input**: glTF URIs (long, `\u`-escaped) and OBJ `mtllib` could make the loader read outside the package. References are decoded as assimp reads them and validated (`MS_CheckModelReferences`); `--inspect-model` refuses such files.
- **Folder scans need their own walker**: raylib's recursive scan overflowed a fixed buffer on long symlink paths and looped on symlink cycles (F9 froze); `src/dirscan.c` uses heap paths, doesn't follow symlinked folders and caps entries and depth.
- **Quadratic lookups show up at scale** (80,000 materials took 18 s): hash tables for names.
- **Dark maps and contrast**: pine_forest rendered 25–36% pure black at `color.contrast 1.08`; fixed in the map (contrast 1), not in R3D, because the R3D fix would change the default map's look (an open decision, `docs/known-issues.md`).
- **Readable diffs matter to the AI workflow**: `--dump-scene` diffs after an inserted line were unreadable (1,504 lines for one lantern), hence `--dump-scene-diff`; a region over a gap listed what lay behind the gap, hence edge objects and per-line shares.
- What held up from the start: the parser, hot reload (every chain matched a direct shot), turn invariance (≤ 0.56/255 drift), frame reuse and the renderer restart (pixel-identical), model placement (within 3 mm), shadow tiles, the fog cache, wine (identical shots), and the end-to-end request workflow.

## One coordinator for all requests (2026-10-24)

Until then every request opened its own terminal with its own `claude` process. With several requests in flight, two sessions could edit the same map at once (the only protection was the map hash check), and code requests could run next to each other while sharing `build/`, the leak check and the GPU; the leak check's cleanup even trashed bundles that were queued during its run. Every request also cost a new window on workspace 10. Now one long-lived **coordinator** session (the `coordinator` skill) takes the requests from a queue on disk and hands each to a subagent, under rules that prevent the overlaps: one request per map package at a time, code requests alone, at most three at once (mechanics: `docs/request-queue.md`). Choices behind it:
- **The file system is the handoff** (`requests/<id>/state`, written whole): the game can't type into a running session. The coordinator sleeps on a shell watcher (`tools/request-queue.sh wait`) whose exit wakes it, so an idle queue costs no tokens. After `queued` only the coordinator writes `state`; the game asks for a cancel with a separate file, so the two never race.
- **A kernel lock says whether a coordinator runs** (`flock` held by a wrapper around `claude`): it survives game restarts and is dropped however the coordinator dies, so the next submit can start a new one safely.
- **Recovery by fingerprint**: a request a dead coordinator had claimed runs again only if nothing in its package or the code changed; otherwise it is reported, because re-running a half-applied edit would apply it twice.
- **Questions go through the coordinator** (`question.md`, then `SendMessage` with the answer). Rejected alternative: `result.md` with `Not done: ambiguous` and a resubmit, because the developer would lose the context and have to aim again.
- **No worktrees**: map edits must land in the real package for hot reload (the developer watches the change appear), and code requests already run alone; the developer's `build/linux/monolith` is the binary to rebuild anyway, and a worktree costs an assimp rebuild of minutes.
- **Code is recognised late on purpose**: only a prompt that plainly asks for engine work starts as code; otherwise the subagent stops before changing code and replies `NEEDS-CODE`, so map requests never wait behind a guess.
- **A dot folder for the queue's own files** (`requests/.coordinator/`): invisible to `ls`-based tools such as the leak check's cleanup, whose earlier version trashed every new folder in `requests/`.
- **The coordinator stays small**: it reads only the queue listing and one-line replies, never images or maps, so a session can last all day.
- The old mode stays behind `MONOLITH_LAUNCH=per-request`; tests use `MONOLITH_REQUESTS_DIR` and a stub coordinator, never a real session.

## Compiled maps (2026-10-25)

Until then every program that used a map parsed its text at load, an exported game included: its runtime shipped the tokenizer, the statement parser, `repeat` expansion and the glTF / OBJ reference scan. Now the text stays the source (editor, hot reload, requests, manual edits, `MS_GetLine`), `monolith --compile` (and `--export`, and `examples/build.sh`) writes `<name>.mapb`, and the runtime without `MONOLITH_EDITOR` reads only that (`docs/compiled-map.md`). Why, and the choices behind it:
- **Why:** a smaller, simpler game runtime with less attack surface, no number parsing of map data at load, and a stable boundary between the editor and games.
- **One parser:** the compiler is the text parser plus a writer of the `SceneData` it fills, so the two inputs can't drift; the reader fills the same `SceneData` and the rest of the load is shared (`FinishLoad`). Verified pixel-identical (text vs compiled) on every map in `maps/` and `tests/models`, every viewpoint, plus identical dumps and entity ids.
- **The parser's state, not the scene:** the file stores what the parser produces before `FinishParse` (boxes already expanded, lights with their defaults, every env key with its final value), not the public structs (pointers, R3D handles) and not derived data. Rejected for now: storing hidden faces, cell meshes or colliders, because they depend on the GPU load or are cheap; worth measuring as a follow-up.
- **Env keys by name** (`CmEnv.key` is a string): the key tables can be reordered and grow without breaking compiled files; a new statement or record field bumps `MS_COMPILED_VERSION` (`CM_VERSION`) instead, and old files are refused with a message to recompile.
- **The reader trusts nothing:** everything is checked before use, with the parser's own rules where they exist (`CheckEnvValue`, `InsidePackage`); `MS_Compile` reads its own output back, so what compiles also loads. Corruption test: `tests/unit/compiled_test.sh` (~18,000 damaged files under ASan + UBSan, no crash).
- **The model-file reference check runs at compile / export, not in games** (the developer's call): a game trusts the model files it ships with, as it trusts its own executable; keeping the JSON / OBJ scanner in games was the rejected alternative.
- **Compiled files are build output, never committed** (the developer's call; `.gitignore` has `*.mapb`): a committed binary could drift from its text. The export ships both, the text as the source.
- **The version is the guard, not layout asserts** (2026-11-02, the developer's call): the records first had `_Static_assert`s on every size and offset (and on the `T_*` values). They duplicated what the file already records (`CM_VERSION` in the header, each section's record size in the table, both checked at load) and made every record change a hand-edit of magic offsets, so they went. The one rule is to bump `CM_VERSION` on any record, section or stored-value change. The trade-off, accepted: a same-size reorder of a record's fields without a bump would misread old files silently; the bump rule and `tests/unit/compiled_test.sh` (which damages fields at fixed offsets) are what catch it.
- Little-endian only (a big-endian host is refused); map line numbers kept (public API, 4 bytes per object); detection by the file's magic, not its extension; editor builds prefer a package's `.map` over its `.mapb`.

## The editor font (2026-10-25)

The editor's text moved from raylib's 10 px bitmap font (scaled to 16–24 px: blurry, uneven) to Outfit, with one UI module (`src/ui.c`) and the panels restyled together (backdrop behind the HUD, key caps, one type scale and colour tokens, pill labels). The choices:
- **Compiled in, not a file:** `build/linux/` and `build/win/` stay copy-as-is folders and nothing is read at run time (`tools/embed_font.py` writes the bytes into `src/font_outfit.h`).
- **Editor only:** the runtime, exports and examples keep raylib's font, so games built from an export carry no font and no extra licence.
- **SIL OFL 1.1 allowed for editor fonts** (the developer's call; CC0 UI fonts are rare). The OFL permits embedding if the licence travels with the program, so `build.sh` copies `OFL.txt` next to the binary.
- **Per-size bitmap atlases, not one SDF font:** sharper at 14–24 px, no shader. All sizes and both weights share **one** atlas that is also raylib's shapes texture, so text and panels stay in one batch; the UI is drawn every frame, also over a reused frame where it is a large share of the time.
- **Rounded shapes from the atlas, not raylib's `DrawRectangleRounded*`:** the first version with raylib's rounded rectangles made the overlay +0.14 ms per frame (0.22 → 0.36 ms, measured around the UI block); nine-slices from atlas discs brought it to +0.05 ms, and key caps baked per line size (3 quads each) to within ~0.005 ms of the old UI.
- **Loaded on first use**, so headless and plain `--shot` runs never create it; plain shots and `view.png` in bundles stay pixel-identical. `view-marked.png` labels changed with the look.

## The editor UI restyle (2026-11-05)

The editor UI read as generic (a warm amber accent, pastel status colours, pills and bordered boxes everywhere). It now follows the developer's site, notfound404.dev; the spec is `docs/ui-design.md`. The choices:
- **Monochrome, colour only as meaning:** translucent black panels, white text at the site's alpha tiers, no accent colour (focus and selection are pure white). Pink / green / orange / yellow / red appear only as a status mark (a 2 px bar + text, the site's `border-l-2` badges), so a colour on screen always says something.
- **No backdrop blur:** it would need an extra pass over the scene every frame; translucency plus a baked soft halo (8 quads, the site's dark box-shadow) stand in. No hero glow and no custom cursor (an editor over a live scene has neither; the site's cursor script is empty anyway). No `active:scale-90` (scaled text blurs).
- **Pixelify Sans, ×3, titles only:** a pixel face is crisp only on its grid (≈ 91/1000 em), which no integer pixel height of stb_truetype matches. It is rasterised at 13 px (cell ≈ 1 px), thresholded into whole pixels and enlarged ×3 with nearest sampling: one crisp size (capitals 21 px). The developer chose ×3 over ×2 (14 px capitals looked thin next to Outfit); at a 39 px line it is too tall for the HUD's 20 px lines, so HUD mode names are marks in Outfit.
- **Request images unchanged:** the region / volume number tabs that `view-marked.png` carries keep the old filled pill (`UiTag`), and the outline colours are scene-side constants, so the request subagents see the same markers as before.
- **Before / after gallery:** one script makes a `--shot --shot-hud` per surface on one map (a dark floor and a bright sky in view); the same script made both galleries.

## CPU profiling (2026-10-25)

A measuring round, no optimisation: where the CPU's time goes in a frame and in a map load, on machine A (AMD CPU, NVIDIA driver). The method is the `benchmarking` skill's "CPU profiling"; the numbers and the ranked candidates are in `measurements.md`. The choices:
- **A separate profile build** (`./build.sh profile` → `build/linux-profile/`, R3D in `build-linux-profile/`), not `-g` and frame pointers in Release: the shipped binary and its benchmarks stay as they were. R3D/raylib/assimp are RelWithDebInfo (-O2) there instead of Release (-O3); measured against Release: pixel-identical shots and identical box and scene dumps on every map, frame time within noise (3 pairs: −0.7 … −1.3%).
- **DWARF call graphs, not LBR or frame pointers:** LBR (the machine-B recipe) is Intel-only; frame-pointer stacks break inside the NVIDIA driver, which has none, but its `.eh_frame` lets DWARF unwinding through it, so driver time is attributed to the R3D call site that caused it.
- **`cycles:u` with a fixed period, chosen below the kernel's sample-rate limit:** the kernel had lowered `perf_event_max_sample_rate` to 2000/s by itself, and the first profiles (1 sample per 1M cycles) were throttled, which drops samples in bursts and biases shares; they were redone. `task-clock` cost ~0.25 ms of CPU per frame (a hook on every context switch of the driver's sleeping wait).
- **Our own report** instead of FlameGraph or similar downloads: code from downloads never runs. First a stdlib Python script (`tools/profile_report.py`), cut down (2026-10-26) to the top CPU functions per frame and the top GPU passes: the developer found the parts, call trees, call-site tables and folded stacks too much.
- **One C program, `tools/profile.c` (2026-10-26)**, replaced `tools/profile.sh` + `profile_report.py`: the developer couldn't follow the shell script (awk inside `$(...)`, pipelines, traps). Now `main()` is a list of named steps; commands run through fork + execvp with an argv array (no shell, no `system()` / `popen()`), each printed before it runs, every exit status checked; the report is computed in C (a port of the Python one: identical output on all 74 profiles of the 2026-10-25 rounds) with `<regex.h>`. A separate tool built by `./build.sh profile`, not a game flag: the game binary stays unchanged and doesn't spawn perf. Cost: glibc's regex makes the report ~2.5× slower than Python's (1 s for a 16 MB `perf.txt`), small next to the recording.
- **No sudo, no sysctl:** `perf_event_paranoid` 2 covers user space of our own processes, which is where the frame's CPU time is (a headless bench with the driver's default spin-wait spends 2.6% of its CPU time in the kernel: 0.24 of 9.2 s).

## CPU optimisations (2026-10-25)

The candidates of the profiling round, each kept only if measured to help and pixel-identical (numbers: `measurements.md`, "CPU optimisations"). Reload of the default map with its first frames 493 → 233 ms, without NVIDIA's shader disk cache 17.7 → 4.7 s; spinning frame CPU −20 %, HUD frame CPU −29 %. The choices:
- **A permanent load log** (`monolith_scene: load|reload … ms: parse, …` and `first frames after the load a + b ms`) instead of scratch timing builds: every load change is measured with the same yardstick, and anyone can see what a slow reload spends its time on. It ships in exported runtimes like the occlusion-volume bake line.
- **Shader aliases, not a shader cache:** every load still compiles each shader file (an edited file recompiles on hot reload, the rule that every cache is rebuilt on reload holds), just once per file instead of once per material. The alias source is a copy no material draws with, because `R3D_LoadSurfaceShaderAlias` copies the source's current uniform values: aliasing the first material's shader would hand its uniforms to every material that leaves one unset. Keeping compiled shaders across reloads (candidate 5) is a separate decision of the developer's.
- **Threads in the runtime** (hidden faces only): pthreads, because glibc has them and MinGW's static winpthreads is already in every Windows build (assimp's libstdc++ pulls it in), so the exports and the examples build unchanged; C11 `<threads.h>` isn't in MinGW. Workers take chunks of boxes from an atomic counter and each box's faces depend only on the boxes, so the result is the same with any thread count; the sorted grid became a hash of cells whose occluders keep ascending box order, so neighbours come in the same order as before (`CoverPieces` gives up after 64 pieces, which is order-dependent).
- **A PNG writer of our own** (`src/png.c`, zlib level 1) instead of stb's compression level: stb never goes below its level 5 and searches 5 filters per row, so its best was −30 %; zlib level 1 on one fixed filter is −75 % and gives smaller files. It uses assimp's zlib, which every build links already.
- **The R3D sort-key cache was dropped** although pixel-identical: −0.01 ms per frame in the profile and nothing measurable in benches. The bar for an R3D patch is a measured gain of ~0.02 ms or more.

## Baked surface tiles (2026-10-27)

The concrete shader was 66% of the geometry pass (`measurements.md`, "nsys: the geometry pass and the concrete shader"), and the pre-pass had already removed overdraw, so only cheaper shading per pixel could help. The choices:
- **A game flag that renders through R3D** (`--bake-surface`, `src/bake.c`), not a CPU reimplementation of the GLSL (it would drift from the shader; numpy isn't installed either): the tile comes from the same file the game compiles, via R3D's existing G-buffer outputs (`R3D_OUTPUT_ALBEDO` / `ORM`), so R3D needed no patch. The defines go only to the baked material's shader, because others sit at R3D's 16 KB source limit.
- **One shader file with a `MS_BAKE` path**, not a separate bake shader: the procedural code and the tiled code live together, so a change to the stone is made in one place and re-baked.
- **`data_sampler`**, a new material key, because samplers load as sRGB colour (trilinear, mipmaps): packed data channels need the raw bytes. The compiled format went to version 2 for it.
- **Every pixel-grid level baked (an atlas), not just the finest:** fetching level 0 at a coarse texel turned the 1-texel veins and cracks into dotted lines, which the grid design forbids.
- **Periodic noise by rounding each lattice to whole cells per period** (the veins' rotated lattice: wrapped modulo two lattice vectors), not cross-faded edges.
- **A baked slice chosen by measurement:** the first slice had 1.9× the shader's average vein area on side faces; the slice 97 m out matches the average cover of veins, cracks and lichen over many planes.
- **Kept procedural:** the per-plane hash, the slow tone and hue noises (continuous across box corners, they hide the tile's repetition) and the height terms (ground grime, lichen below 3 m).

## Live editing (2026-10-28)

Edit mode used to write every key press into the map file and run a full `MS_Reload` (~520 ms plus a cache redraw on the largest map), which made fine placement and any drag unusable. The round (design: `docs/live-editing.md`) made edits live in memory, added the G / R / S transform modal, the id panel, the render inspector and the model picker. The choices:
- **The working copy is map text, not a list of ops applied to the scene arrays.** Each edit is still `mapedit.c`'s minimal text patch, against an in-memory text; `MS_EditSetText` parses it again on the CPU and swaps in only what changed. Save + reload is then identical to the live scene by construction (it *is* the parse of the bytes CTRL+S writes), object order stays the map order (draw order, hidden faces and raycast ties depend on it), and requests, hot reload and the AI keep reading text. The cost is the re-parse (~26 ms of the ~43 ms per edit on the largest map); drags therefore use a preview (`MS_EditPreview*`) that moves objects without text and commit one op at the end. Steps keep their op and selection ids so they can be applied again to a changed file (the rebase).
- **The diff is by content, not by entity id:** the pieces of a split `repeat` line get new implicit ids although their boxes didn't move.
- **Dirty regions instead of a version bump for the caches:** `scene->version` still changes with every edit (frame reuse, the selection, bundles need that), but a live edit re-stamps the caches after invalidating only the sun tiles, light shadows, fog bake and AO voxels its changed objects reach, so the game build's cache code stayed as it was. A cache whose *region* depends on the content (fog / AO region, tile home) is redone in full when that region moves, as a reload would.
- **Both save modes** (the developer's call): manual CTRL+S by default, `edit_save = auto` writes each edit at once; a request needs the file saved first, because the bundle's lines and hash describe the working copy.
- **RMB-held flying in edit mode** (the developer's call) frees the letter keys for Blender's G / R / S / X / Y / Z.
- **The inspector's filter hides ranges from every pass and redraws the shadow caches**, so a hidden object drops its shadow; the fog bake waits while something is hidden (R3D bakes from the frame's draw list).

## Free rotation (2026-10-28)

Boxes were **axis-aligned everywhere** from round 1: the format (two corners), the colliders and their BVH (AABB overlap), `MS_Raycast` (slab test, axis normals), hidden-face removal and the merged per-cell meshes (only axis-aligned faces can cover each other exactly), the AO volume (an AABB distance), the compiled records and the dumps. That kept every one of those paths simple and exact, and the default map (a grid of concrete) never needed anything else; a diagonal was a model or a staircase of boxes, and the edit mode turned boxes only in 90° steps about the vertical (the corners swapped). Placing ramps, leaning slabs, beams and fallen rubble by eye made that too slow, so the developer decided (design: `docs/live-editing.md` §11):
- **Boxes and blocks turn freely, like models** (`box … rot y p r`, the models' `R = Ry · Rx · Rz`, about the box's own centre). Stairs, waffles and lights don't.
- **A turned box collides as its turned shape** (a separating-axis test, and `MS_ColliderTop` for landing and stepping), not as the AABB around it; the player walks slopes up to 46°.
- **`boxes[]` and `colliders[]` keep the world AABB** of a turned box and the exact shape sits beside them (`turnedBoxes` / `boxTurned`), so everything that uses boxes as bounds (clusters, culling, dirty regions, hover) needed no change, and **every new path runs only for a box that has a rotation**: maps without one are bit-identical in every dump and shot (the round's acceptance test). Turned boxes take no part in hidden-face removal and get their own per-cell ranges, so the axis-aligned meshes stay byte-identical.
- **The editor writes the simplest form:** a box whose pose ends axis-aligned (any 90° multiple) is written as plain corners without `rot`.
- **Controls follow Blender:** plain R is a 90° step about the vertical (no free control), ALT+R the keyboard modal, ALT+SHIFT+R the reset, plus a rotate gizmo (axis rings, view ring, trackball) whenever something that can turn is selected.
- **Compiled maps went to version 3** (one record per turned box, the boxes stored as written). Version 2 was read too, until 2026-11-12 ("One map format in the code").

## Error messages without a message buffer (2026-11-02)

The parser's `Fail` and the compiled-map reader's `CmFail` used to format the message into a local `msg[512]` / `msg[400]` and then copy "<file>: <msg>" into the caller's `err`; a few parser checks (`Keyword`, model-file references) pre-formatted into their own `m[256]` / `msg[]` first. Those messages hold content (tokens, names, paths), so a long one was cut twice, silently, before the caller's buffer even mattered, and could end in half a UTF-8 character. Now one helper, `MsErrorV`, writes the prefix and the message straight into the caller's buffer; the caller's `errSize` is the only limit, and a cut keeps the file and the start of the message, NUL-terminated and on a character boundary (`tests/unit/compiled_test.sh` with its `longname` package, `tests/unit/parse_error_test.sh`). The defaults chosen:
- **The caller's buffer, not a heap string:** a failure path is also the out-of-memory path, so it must not allocate, and the API (`char *err, int errSize`) is caller-sized already.
- **No change to the API or to any message text;** the editor's own `char err[512]` buffers in `src/` are callers' buffers and stayed (a long message reaches the editor's terminal cut at 511 bytes, cleanly).

## Painting (2026-11-03)

The developer wanted to put marks, signs, decals and pixel art on objects by hand instead of describing them in a request. Draw mode (B) paints on boxes and models in the editor (design: `docs/painting.md`; four phases by agents in worktrees, merged by the lead, two independent verifiers). The developer decided:
- **"Pixel size" is two controls:** the brush size in texels and the canvas density in texels per metre (new canvases; Resize to density), plus `filter nearest` for a pixel-art look.
- **Each object gets its own texture:** the first stroke copies its material as `paint_<id>` with `textures/paint/paint_<id>.png`; a Shared switch paints the material's own texture instead.
- **The developer says which box faces share texture space:** `uv_faces a b c d e f` (+x −x +y −y +z −z; faces with the same number share a cell). Box UVs were 0–1 on every face from R3D's unit cube, so one face's paint showed on all six; the key is opt-in, so every unpainted map stays bit-identical (the round's acceptance test).

How it fits the earlier rounds: paint is pixels plus the smallest text edit, so requests, hot reload, compiled maps (version 4) and the export keep reading the package; strokes are steps of the live-editing history (undo tiles, rebase replays strokes onto a PNG that changed on disk); the runtime only receives pixels (`MS_TextureProvide`, `MS_TextureUpdate`) and says where a ray hit a surface (`MS_RaycastSurface`). Lessons:
- **A scripted shot can reach the real launcher.** A `--draw-panel` test's ENTER reached the designer, opened the prompt box, submitted bundles and started a coordinator in a visible terminal on the developer's screen. Since then the launcher refuses to open a real terminal from an agent's shell unless `MONOLITH_TERMINAL` is a stub, and draw-mode / panel input never reaches the designer.
- **A freed vertex range can be drawn with its old contents** when back-to-back live edits free and refill it before a frame is drawn (NVIDIA 615.71; R3D's shared vertex buffer). It also explained a nondeterministic sun shadow after live edits from before the round. Live edits now free replaced meshes after the next draw (`LiveRetire`).

## The paint layer (2026-11-04)

The first painting round's model, paint in a copy of the object's material, changed how objects looked and refused too much. On the default map 97 % of the boxes use surface-shader materials, so a shader bake was added (`src/surfacebake.c`: the shader rendered into the canvas from R3D's G-buffer views on the first stroke), but a baked box blurred finer detail, froze animation, lost its emission, specular and view-dependent shading, got pixel-grid edges; a copied flat colour moved the light nearby by 1–2 levels; model slots with shaders, forward-pass shaders and shared mode on flat colours stayed refused. The developer wanted painting to change nothing but the painted texels, anything to be paintable, and no cost in the exported game. The second round replaced where paint lives (`docs/painting.md` §1–§9; the bake is in the first commit of the branch, `3bc1bc4`, and was then removed):
- **Paint is a layer, not a material.** The material, its shader and textures stay untouched; each painted material has a per-material atlas (`paint` key) and `paint` statements give each painted box face (group) or model slot a rectangle. A generated paint stage wraps the material's own surface shader (or an empty one) and composites the atlas at the end of the fragment stage.
- **No new draws.** R3D's vertex has one half-float UV set and no second channel, so which paint a face uses rides in data R3D binds but these draws don't use: merged box meshes carry the paint key and face corner in the vertex bone channels, instanced boxes and model instances carry it in `INSTANCE_CUSTOM`, and a per-scene table texture maps keys to rectangles. Painted objects stay in their material's draws; unpainted maps run nothing new.
- **The developer decided:** commit the first round as it stood and build on it; models whose UVs overlap or repeat get a generated unwrap per model file (xatlas, MIT, vendored, editor only; a `.paintuv` sidecar the runtime reads); "no slower" means within noise in the exported game, with one extra texture sample per pixel only on painted materials.
- **Measured with the exported runtime itself:** the examples' test harness got a headless bench mode (`--bench`) and `tools/bench-export-ab.sh` runs interleaved A/B pairs of two exports, so the claim is about the shipped game, not the editor.

Lessons:
- **Draw order is part of the look.** R3D sorts draws by its shader serial (patch 17) before textures, and the first draw wins at equal depth. A material that gains a shader (or an alias made again by a live edit) moved in that order and changed which of two touching surfaces showed (157 pixels where trunks meet the ground, from an alpha-0 paint entry). R3D patch 27 lets the caller set the sort key; the runtime gives each scene material its load's key whatever is painted.
- **R3D's surface-shader parser is textual:** entry points are found by the text `void vertex` / `void fragment`, global code goes into both stages, varyings only into the stage sections, and a token starting with `flat ` is taken for a varying. Wrapping a shader means renaming its entry functions under stage guards and writing its varyings as `in` / `out` in place; the 16 KB source limit is met by stripping comments.

## Private maps and the weed pre-pass (2026-11-05)

- **`maps/monolith` is a submodule of its own closed-source repository** (`113f06a`): this public repo holds only the pointer, never the package's files. Map changes are committed in the submodule, then the pointer here. Merging a newer package with local work: three-way, with the pre-bake backup as base, keeping all of the newer package's content and adding only the bakes and engine-driven keys.
- **R3D patch 28 (`prepass off`):** measured first (flat `fragment()` saved nothing, removing the weeds 2.2 ms), so the weeds' cost was triangles drawn twice. A per-material opt-out was chosen over a heuristic (triangles ÷ shader cost isn't known to R3D) and over greedy-meshing the voxels (larger, later). Gain −0.5 ms on machine C, smaller than the estimate (~1 ms): the depth-only draws were cheaper than the shading draws.
- **Volumetric fog on an integrated GPU:** the developer asked why it is heavy before making it cheaper. The answer (r3d-pitfalls §1): the map's fade turns off the shader's shortcuts, so sky pixels march fully, and the per-step lookup dominates. Next: skip lookups in uniformly lit or shadowed air (bit-identical), then a closed form for fully lit rays.

## The runtime owns the last error (2026-11-06)

The 2026-11-02 round left the caller's `char *err, int errSize` as the only limit, and every caller passed 512 bytes while `MS_PATH_MAX` is 1024: a message quoting a deep path lost its reason (a 657-byte map path came out as 512 bytes of path, no "file not found"), and the "several map files" message listed 5 of 100 candidate names (`ResolveMapPath`'s `names[512]`). The developer wanted messages with no length limit and accepted an API break. The runtime now keeps its last error in a heap string it owns (`MS_LastError()`); every public function lost its `err, errSize`, and failure is the return value. The defaults chosen:
- **Per thread (`_Thread_local`), not main-thread only:** the box-hiding workers never set an error, but a game may load scenes from its own threads; MinGW builds it too.
- **Success clears it** (as `LoadBytes`' `err[0] = '\0'` did); `MS_Poll` leaves it alone when it reloads nothing. Valid until the next `MS_*` call. A clear keeps the memory; a new message is built before the old one is freed, so it may quote the old one (`ResolveMapPath` wraps `PackageFile`'s appended name list this way).
- **`MS_ClearError()`** frees it, called at exit (the editor's `main`, the examples, `viewer.c`), rather than relying on the leak checker seeing TLS as reachable.
- **Out of memory while building a message gives a static "out of memory"**, never NULL or half a message. The old argument for caller buffers (the failure path must not allocate) is answered by that fallback.
- **The editor shares it** (`MS_SetError` / `MS_AppendError`, editor builds), `src/paintunwrap.c` included, so a runtime message is never cut back one layer up; `MS_Error(scene)` became a heap copy, and the launcher's coordinator error too. `GfxLoad`'s "N lines ignored" was a warning on success, so it became an out-count instead of an error.
- **Message texts unchanged**, except that nothing is cut: two edge cases now say "path too long" (a path longer than `MS_PATH_MAX` was silently cut before it was opened; a single map file whose path didn't fit said "more than one other .map file").
- The UI's own status buffers (`msg, msgSize` of the edit, draw and export modes, raylib's `TextFormat`) were display buffers and still cut a long message on screen; the terminal and the log got it whole (until the status-code round, 2026-11-09, below).

## The build program: nob.c (2026-11-09)

`build.sh` had outgrown a shell script (stamp files, configure-argument tracking, a Python program embedded for `compile_commands.json`). Its logic moved into one C program, `nob.c`, written on the vendored nob.h (3.10.1, unmodified, `src/vendor/nob/`); `build.sh` only compiles it into `build/nob` and `exec`s it. Same mode names, arguments and environment variables.
- **Why nob:** one header, plain C like the rest of the repo, commands as argument lists (no quoting or word-splitting surprises), and it rebuilds itself. Like `tools/profile.c` (2026-10-26), the build should read as a list of steps, each with a comment that says why.
- **Nothing built changed.** Proven per mode (plain, `debug`, `lsan`, `profile`, `--win`) against the old script: the argv of every command identical (tool wrappers logging them), every output's sha256 identical (game, profile tool, `.exe`, `xatlas.o`, stamps, args files, `maps/`, even `compile_commands.json` byte for byte), the incremental second run as quiet as before. `R3D_BUILD_TYPE=None` and other compilers were compared as dry runs with stub tools (a real run would rebuild all of R3D twice). The `--win` exe is only reproducible with `SOURCE_DATE_EPOCH` (PE link timestamp), for the old script as well.
- **Per-command timing** (the reason the developer asked for a C build): nob.h doesn't measure anything (`waitpid`, no resource usage), so `RunTimed` takes the wall time around each command and CPU time as the `getrusage(RUSAGE_CHILDREN)` difference. That is exact because commands run **sequentially**: one waited-for command at a time, and every compiler of `cmake --build -j` is a waited-for descendant. Parallel commands (`.async`) would mix their numbers, and parallelising the build was out of scope. **No CPU cycles:** a `perf_event_open` user-space cycle counter with `inherit` was proposed (with an `n/a` fallback where the PMU isn't available); the developer chose wall and CPU time only.
- **Output:** nob's `[INFO] CMD:` echo and the `[TIME]` lines are printed, on stdout with the old progress lines, so the leak check's `./build.sh lsan > /dev/null` stays quiet. The `built:` / `wrote:` texts are unchanged.
- **python3 is no longer needed** to build: the `compile_commands.json` writer is C (it reproduces `json.dump(indent=1)` exactly, so switching never shows a diff).
- First reading of the summary: a full plain build (fresh xatlas, re-configure) spends ~80 % of its time in the one game compile+link command (~11 s of ~14 s), ~17 % in the xatlas compile; R3D's configure and no-op build take ~0.4 s together. The Windows game compile is the slowest single command (~20–24 s). An incremental build is still ~11–14 s, almost all of it the game command, which always recompiles every file; its CPU time equals its wall time, so one compiler process compiles the ~35 files one after another. Per-file objects compiled in parallel would be the next step, as its own round (the timing would then need per-command attribution that survives parallel runs).

## Status codes instead of message buffers in `src/` (2026-11-09)

The 2026-11-06 round gave the runtime a heap last error but left the editor's own pattern: functions filled a caller's `char *msg, int msgSize` (`char msg[512]`, `[1400]`, …), and callers printed it, showed it, or decided by it (`if (msg[0])`, `strncmp(m, "nothing to save", 15)`). The `engine-code` rule already forbade `char *err, int errSize`; `src/` had kept the same thing under the name `msg` because it also carried success text ("saved 3 lines"). Three problems: 512–1400 bytes of stack for a short sentence, some in the frame loop (`main.c`'s `msg[512]` for an `EditModeSave` nobody read); text cut without a warning (the spectator's 128-byte line cut a 128-character coordinator message to "…close it by han"); and logic that depended on wording. The developer asked for the pattern to go and for the rule to cover success and status text too. The defaults chosen:
- **Plain `unsigned char` statuses, 0 = success (POSIX)**, the values listed in the function's comment; no enums or named constants (the developer's call), so a call site reads `== 2 // not saved`. The polarity flip from `bool` was the main risk; every call site was reviewed for it by the agents and an independent verifier.
- **One place per code for its sentence:** `MS_LastError()` for failures (as the runtime does; a fixed failure text that shares a code with detailed ones goes there too), the owner's `MonoMsg` note for the other outcomes (`MapEditNote`, `LauncherNote`, `ExportNote`), or a literal the caller picks by the code (`TransformBegin`'s "nothing selected"). A callee whose result the caller only printed reports it itself (`EditModeSave`, `ExportScene` with a `console` flag for `--export`'s stdout/stderr vs F9's log).
- **`MonoMsg` (`src/msg.h`, editor only):** a literal kept as a pointer, or a heap string sized in two `vsnprintf` passes; out of memory falls back to the static "out of memory". Setters come in pairs (`…Static` for literals, `…f` for run-time text) and the old names were removed, so every call site had to be looked at. It stays out of the runtime until the runtime needs it.
- **Words unchanged:** every console line, HUD text and bundle stayed byte-identical (a capture of the leak check's runs plus every map's views and exports, logs normalised, images compared outside the frame-time strip). The only visible difference is that text a buffer used to cut is now whole. Explicit precisions in formats (`%.80s`) are wording and stayed.
- **Kept:** formatters bounded by a few numbers (`MapEditStatsText`, `MapEditIdText`, `MapEditDescribe`, `GfxRowFormat`), path scratch (`char path[…]`, `GfxUnsavedPath`), and the runtime's `MS_GetLine(…, out, outSize)` (a public API copying one source line; a heap return would need the developer's yes). `MapEditSync` had no caller and went.

## The stated purpose (2026-11-10)

The texts described a cross-platform "map designer for 3D levels of any style" and left out what the developer sees as the project's value. The purpose was restated (descriptions only, no code changed) in `CLAUDE.md`, the README, `docs/architecture.md` §1/§2/§6, `docs/export.md` and `src/main.c`'s first line, as three points:
- **Deterministic edits, with AI.** The AI decides *what* changes; the change goes through deterministic, checkable paths: the `.map` text, the edit language (`src/mapedit.c`), the compiled map (same bytes on every compile), deterministic rendering (patch 17), `--dump-boxes`, `--dump-scene-diff` and pixel-compared shots. This is the reason those paths exist (round 1's one primitive per line, the compiled map's one parser, the QA pass's readable diffs) said once as a goal.
- **High-quality, optimised exported C.** `--export` writes plain C11 held to the editor's rules (stripped runtime, no fixed-size content buffers, failure as a return value, zero warnings and leaks, no per-frame allocation, measured caches and presets).
- **The editor is Linux + i3 only; the exported code is portable.** The editor (game, launcher, coordinator, tools) is made for Linux with i3; sway and the other i3-related paths stay as they are. Windows and macOS editors aren't supported or considered in decisions. Exports and the examples build for Linux and Windows x86_64; other export platforms are untested.
- **Why `./build.sh --win` stays:** it builds the static Windows libraries every export ships in `prebuilt/win/lib/` and compile-checks the runtime for Windows, so the both-targets zero-warnings rule stays, its reason now "exports and the runtime run on Windows". `build/win/monolith.exe` is a by-product. The editor's Windows code (the launcher branch, `tests/unit/wincmd_test.c`, the `%APPDATA%` settings path, `--win run` under wine) is still there and called unsupported; removing it is a separate decision.
- **The view-only build (2026-11-10, the same day):** that decision was taken, but not as "remove": the editor built for any platform but Linux (`MONOLITH_EDITING`, keyed on `__linux__` in `src/common.h`) became a supported **viewer** for benchmarking, viewing and debugging a map: everything that edits, produces deliverables (`--export`, `--compile`, F9) or reaches the AI is refused at its entry point (`src/main.c` header, "View-only build"). Why the viewer stays: opening a map on Windows to measure frame time on another GPU, look at it or debug a driver issue is worth having and touches no map text, while the editing paths elsewhere were compile-tested only, a maintenance cost with no user. Removed with it: the launcher's Windows branch (`cmd /c start … cmd /k`, the `9>` lock, `_spawnvp`), `src/wincmd.c/.h`, `tests/unit/wincmd_test.c`, `import.c`'s Windows branches; `launcher.c` / `import.c` are no longer in the Windows build. Kept: the `%APPDATA%` settings path (the F2 panel saves there), `--win run` (the documented way to open the viewer under wine), hot reload (it only reads).
- "Levels of any style" is unchanged: the purpose changed, not the style-agnostic rule.

## One map format in the code (2026-11-12)

The developer's task "Version Convention: No need for backward compatibility in monolith", with the direction that **map format migration is done by AI**. Until then the parser read format 1 (no format line) and format 2, the legacy `at` prefix stayed in the language to reproduce the first map's C loops, the compiled reader accepted versions 2 to 7, and the bundle reference described formats 1 to 4. Every format change added a branch that stayed forever.
- **The convention:** the code reads exactly one version of each of monolith's own formats: the map text (`MS_FORMAT_VERSION`), the compiled map (`CM_VERSION`) and the request bundle (`"format"`). A version number is a guard. Any other version is refused with a message that says what to do. No code branches on an old version and nothing migrates in C. The rule is in the `engine-code` skill, "Change the map format".
- **Why:** one parser path and one reader stay small and checkable, which serves the stated purpose (deterministic paths, 2026-11-10). Migration is rare and needs judgement, so it went to the AI with a proof rather than into code that carries it forever.
- **How a map is migrated:** `/migrate-map <package>` (the `migrate-map` skill) rewrites the `.map` step by step, following `.claude/skills/migrate-map/versions.md`. Each step names its `last-reader:` commit. The skill builds that commit (`tools/old-monolith.sh`) and proves the result against it: the same `--dump-boxes`, the same `--dump-scene` apart from the format number, and 0 changed pixels at every view. It keeps the original as `<name>.map.v<N>` next to the map.
- **Format 3** was the first real migration: the format line became mandatory (a file without one counts as format 1) and `at` was removed. Folding `at` into a line's numbers isn't always the same float (`(-36 + 4.5·i) + 2.6` vs. `4.5·i + -33.4` differs in the last bit for 14 of the first map's 17 roof beams), so a line whose fold isn't exact gets a leading `repeat 1 x y z from 1` instead. It reproduces the same additions in the same order (apart from a literal `-0`, which the proof catches).
- **The developer's two calls:** (1) in-game migration is a **message only**: the game names `/migrate-map <path>` and the user runs it in their own Claude Code session. There is no key, no `"migrate"` bundle kind, and no coordinator change (a queued migration would hold the queue behind an old-commit build); the key is an `idea:` in `.claude/TODO.md`. (2) **No proof, no migration:** when the old version can't be built (no git history, a missing commit, a failed build) or any proof fails, the skill refuses and leaves the map byte-identical. There is no "unproven" result.
- **Defaults taken:** version numbers are never reset. The skill works only on maps inside the repo (an outside map is copied into `maps/` first). A shot that differs while both dumps are equal is a failed proof. `CM_VERSION` stayed 7: the layout didn't change, and the new header check (`formatVersion` must equal the current map format) already refuses every older file. The bundle went to format 5 for edit and import bundles alike, without `omittedObjects`, and old bundles in `requests/` are left alone. Exported packages ship their own runtime and compiled map and are never migrated. `monolith_scene.h` makes no API stability promise.
