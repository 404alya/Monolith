# Export

How to use a monolith map in your own raylib + R3D program. (The other direction, bringing a project's scene into monolith, is `--import`: [user-guide.md](user-guide.md).) Code: `src/export.c`, `runtime/export/`; [architecture.md](architecture.md) §4.3.

`monolith --export <dir> [--map <path>]`, or **F9** in the game (the open map, into `export/<map>-<stamp>/`), writes one map as a self-contained folder: someone extracts it on a clean machine, runs `./build.sh` (Linux) or `./build.sh --win` (MinGW-w64), and gets a viewer that draws the map exactly as monolith does, with the map's viewpoints. Layout:

| Path | What |
|---|---|
| `<name>/` | the map package: `<name>.mapb` (the compiled map, [compiled-map.md](compiled-map.md): what the viewer and the runtime load), `<name>.map` (its source, byte for byte; never read by the program, kept so the map can be edited and compiled again), `MAP.md`, `ASSETS.md`, every file the map references, sidecars, licence files next to them, the files model files refer to (`.gltf` URIs, `.obj` → `.mtl` → maps). Unreferenced files are listed, not copied. |
| `monolith_scene.h/.c` | the scene runtime **without its `#ifdef MONOLITH_EDITOR` blocks**: no text parser (it reads only the compiled map), no compiler, hot reload, source lines, writers or editor toggles; loading, drawing, quality presets, spawn / viewpoints / colliders and the queries stay. `tests/unit/export_strip_test.sh` checks that no parser is left |
| `viewer.c`, `build.sh` | from `runtime/export/` with `@MAP@` = the map's name: a plain example program (window, fly camera, viewpoint names on screen) and the one-step build (R3D + raylib + assimp as static libraries via CMake, `-DMS_PATCHED_R3D`) |
| `r3d/` | the patched R3D monolith builds with (`submodules/r3d` or its `R3D_DIR`), with `patches.md` and the vendored raylib, assimp, glad, tinycthread, uthash; only what a build reads (`R3D_KEEP` / `R3D_SKIP` in `src/export.c`; no `.git*`, build folders, examples, docs, tests): ~33 MB |
| `prebuilt/<linux\|win>/lib/` | `libr3d.a`, `libraylib.a`, `libassimp.a`, `libzlibstatic.a` exactly as monolith's `build.sh` built them from that tree (R3D's GPU profiler compiled in, off at run time): `build.sh` only compiles the viewer and runtime and links (~2 s); if that link fails (an older toolchain or glibc than the machine that built them; for example gcc 16 / glibc 2.44) it builds from `r3d/`, as `--from-source` always does. A target is left out, with the reason in the log, when its libraries are missing, not a static Release build, or its last build (`monolith-build.log`) failed or ran before the newest R3D / raylib / assimp source changed: run `./build.sh` / `./build.sh --win` before exporting. ~26 MB for both targets |
| `cmake/`, `LICENSES/`, `README.md` | the MinGW toolchain file; the licence texts of monolith (MIT, for the runtime, `viewer.c` and `build.sh`), R3D, raylib, assimp and uthash; the README (bundled build first, using the scene in another program, own R3D as the alternative, patched vs. upstream R3D, quality presets, depth clamp, licences + the `ASSETS.md` table) |

Nothing partial: every source is checked first (a referenced file that is missing fails the export and nothing is written), then the folder is written as `<dir>.partial`, the copied `.map` compiled there (`MS_Compile`), the compiled map loaded again and the folder renamed. Exporting a compiled map (`--map x.mapb`) exports its source `.map` instead, which must be next to it and unchanged since it was compiled (a stale one is refused). R3D and the runtime read nothing else at run time (R3D's shaders and lookup tables are compiled in). The export needs the repo (a copied build folder can't export). Keep packages exportable: package-relative paths only, every file recorded in `ASSETS.md`.

Build needs on the target machine (not bundled): with the prebuilt libraries a C compiler, the C++ runtime and on Linux libGL / X11; from source also cmake ≥ 3.22, python3 (R3D's shader embedding), a C++ compiler and on Linux the X11 / GL development headers (listed in the README); `--win` the MinGW-w64 cross-compilers.

## Using the scene in your own program

The exported `viewer.c` is the complete example. Ship the package folder with your program: `MS_Load` on the folder opens its `<name>.mapb` (the `.map` can stay behind; after changing it, compile again with `monolith --map <name> --compile <name>/<name>.mapb`). The call order: `InitWindow`; `R3D_Init`; `MS_InitRenderer`; `MS_Load`; `MS_ApplyEnvironment` (+ `MS_ApplyQuality` for a quality preset) + `MS_ApplyRenderResolution`; per frame `MS_Draw` (or `MS_PushLights` + `MS_DrawGeometry` inside your own `R3D_Begin` … `R3D_End`); `MS_Unload` before `R3D_Close`. Collision and picking: `MS_Collides`, `MS_Raycast`. `scene->colliders` are world AABBs: for a box written with `rot` (a turned box, listed in `scene->turnedBoxes`, found through `scene->boxTurned[i]`, which is NULL when no box is turned) the entry is its bounds, and `MS_Collides` / `MS_Raycast` test its turned shape; `MS_ColliderTop` / `MS_ColliderBottom` give a collider's surface over a footprint (standing on a slope). The API is documented in `monolith_scene.h`; the examples in `examples/` (in this repo) show a minimal program, adding a scene to an existing project, and live editing.
